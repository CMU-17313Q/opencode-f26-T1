## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R2 | When the student asks why something failed, the explanation describes the cause without proposing a fix. It ends by asking whether they want help fixing it. | The explain_error result never proposes a fix. It tells the agent not to include one and to end by asking whether the student wants help with a fix, and the response check flags any reply that proposes a fix. | Checkability. The reply is written by the language model, so code can't guarantee its wording, and a test can't check it deterministically. The tool controls its own result and the response check that detects a fix in a reply, so the requirement now covers those. The need from C-3, C-4, and O-4 (no fix until the student asks) is unchanged. |
| R5 | The explanation covers only the most recent failure. Messages sent after it don't change it. | The explanation covers only the most recent failure. Earlier failures, and later messages that are not a passing rerun of the failed command, don't change it. | Conflict with R8. R8 (C-6, S-6, O-6) requires the explanation to say when the failed command was rerun and passed, but R5 said no later message may change it. C-8 and O-8 were about unrelated messages ("rename this button"), so R5 now excludes only a passing rerun of the same command. |
| R7 | Every file and function listed as evidence appears in the failure output, or is a file the student attached. | Every file and function listed as evidence comes from the recorded failure: it appears in the failure output, is a file the student attached, or is the file the failed step was working on. | Conflict with R3. When an edit fails, the tool knows which file the step was editing, but that file is often not in the error text (for example "oldString not found in content"). The original wording would force the tool to drop it, and R3 would then report "which file failed" as missing although it is known. C-9 and O-9 objected to evidence that was not in the failure record, which the revised wording still rules out. |

R3, R4, R6, R8, and R9 are kept as written: each names a concrete input and an output a test can check, and none conflicts with another.

## Run, triage, and fixes

First run: the final property file against unmodified `main` (`97eb0bc`), seed `17313`, 200 cases per property. R2 (tool result), R5, R6, and R7 passed. Five failed:

| Property | Shrunk counterexample | Triage | Fix |
|---|---|---|---|
| R2 response check | A well-formed reply plus a `### Solution` section was not flagged. `### How to fix it` was also missed. | Code bug: the fix-heading pattern only knew "fix", "proposed fix", "suggested fix", and "the fix". | `check()` also flags "how to fix" and "solution" headings. |
| R3 | `src/a.ts(1,1): error TS2307: Cannot find module 'a' ...` gave high; the model expects medium. | Code bug, same cause as R4: a known location made an ambiguous cause "high". | Unresolved imports stay medium even with a location. |
| R4 | `error: Cannot find module 'lodsh' from '/repo/src/index.ts'` got the hint "A module, file, or folder the code needed was missing." | Code bug: new requirement, not implemented. | A separate hint for unresolved imports names both causes. Vite's "Failed to resolve import" is recognized too. |
| R4 (after the fix) | The new hint says "may not be installed"; the property looked for the exact words "not installed". | Wrong test: the hint names both causes, the check was too literal. | The property matches `/not (be )?installed/`. |
| R8 | `bun test` fails at `math.test.ts:8`, then passes: nothing mentioned the passing run. | Code bug: new requirement, not implemented. | `ErrorContext.latest` marks a later passing run of the same command, and the explanation says so. |
| R9 | The same `math.test.ts:8` failure pasted: "Missing" did not list the command. | Code bug: new requirement, not implemented. | A pasted error lists "which command was run" as missing. One existing unit test was updated to expect it. |
