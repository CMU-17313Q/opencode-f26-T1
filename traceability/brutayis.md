# Traceability: Belard Ange Rutayisire (brutayis)

**Target feature:** Guided debugging. When a command fails, OpenCode explains the error in a fixed four-part format (What went wrong, Where it happened, Why it happened, How sure I am), then shows a testing strategy, and shows a fix only after the student asks. Main source files: [error-explanation.ts](../packages/opencode/src/session/error-explanation.ts) (evidence and response format), [explain-error.ts](../packages/opencode/src/tool/explain-error.ts) (explain_error tool), [testing-strategy.ts](../packages/opencode/src/tool/testing-strategy.ts) and [guided-debug.ts](../packages/opencode/src/tool/guided-debug.ts) (flow and consent).

Interview evidence IDs refer to my P4A workbook: S = staff interview, C = classmate interview (Sultan), O = outside interview (Marco). All properties are in [error-explanation.property.test.ts](../packages/opencode/test/session/error-explanation.property.test.ts) and run 300 generated cases each.

## Requirement changes

The final reply to the student is written by the language model, so no test can check its exact wording. I check each requirement at the explain_error and guided_debug output: the evidence they collect and the instructions they give the agent. R2, R3 and R4 could be checked that way as written and stay the same.

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R1 | Guided debugging never shows or applies a fix until the student explicitly says they are ready for it. (Acceptance: OpenCode makes no edit or write tool calls after "not yet".) | guided_debug only tells the agent it may present the fix after the student picks "Review testing strategy" and then "Show proposed fix". Any other answer keeps the fix hidden. | Checkability and feasibility. Whether the model makes an edit call is up to the model and the student's permission settings, not something guided_debug can guarantee or a test can check for every input. What S-1, S-3 and S-11 needed was to be consulted before any change, and the consent gate in guided_debug is the part of the feature that controls that. |
| R5 | When the error is not recognized, the explanation says it is not sure instead of stating a cause as fact, and lists the error lines it used as evidence. | When the error matches none of the known error types, the explanation gives no hint, sets confidence to low, tells the agent to say it is not sure and what would help, and lists the error line it used as evidence (the first line that mentions an error, otherwise the first line of the output). | Checkability. "Not recognized" and "the error lines it used" were vague. The revision defines both precisely. Running the R5 property also showed that crash messages such as "Killed" and "Process terminated with signal 1" contain no word like "error", so they were never cited at all (see triage below). The revision keeps what C-2, C-6 and O-4 asked for: say when it is guessing and show the evidence. |
| R6 | The "Where it happened" section names the file and error line the explanation is based on, so the student can check it, and says so when no location is known. | The explain_error result names the file and error line the explanation is based on, and when no location is known it names no file, lists "which file failed" as missing, and tells the agent to say so in "Where it happened". | Checkability. "Where it happened" is written by the model, so the requirement now applies to the evidence and instructions explain_error gives the model. It still gives O-8 and C-6 the file and line they wanted to check. |

## Run and triage

All five properties failed on the first run against `main`. Each failure was a code bug. All were fixed in [error-explanation.ts](../packages/opencode/src/session/error-explanation.ts), and every property now passes, along with the existing error-explanation, explain-error and guided-debug tests.

| Property | Shrunk counterexample | Outcome | Fix |
|---|---|---|---|
| R2, R3, R6 | A stack frame at `/repo/a.svelte:1:1` (R3: `/repo/a.astro:1:1`) | Code bug: the location pattern only accepted extensions of 1 to 4 letters, so `.svelte` and `.astro` files were never found, and "which file failed" was reported as missing even though the output named the file. | Accept extensions of up to 10 letters. |
| R4 | Task `"   "` (spaces only) | Code bug: a blank task counted as given, so "what the student was trying to do" was not listed as missing, and the summary said "while working on: ." | Trim the task before checking it. |
| R5 | `"Process terminated with signal 1"` | Code bug (plus requirement made precise, see R5 above): crash messages without the word "error", "fail" or "exception" were never cited as evidence, so a low-confidence explanation had nothing to show the student. | Fall back to the first non-empty line of the output. |
